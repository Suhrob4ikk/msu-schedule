# МГУ Душанбе — Расписание занятий

Приложение с расписанием занятий филиала МГУ им. Ломоносова в Душанбе. Данные берутся
с официального сайта **msu.tj**. Три части: backend (API), web (сайт), mobile (Android).

Язык общения с пользователем — **русский**. Пользователь — владелец проекта (не всегда
технический): объясняй простыми словами, делай сам, не проси подтверждений на мелочи.
На деплой в прод и на необратимые действия — спрашивай.

Аудитория — примерно 20–30 студентов. Нагрузка мизерная, оптимизировать под масштаб не нужно;
цена ошибки — не в производительности, а в неверных данных на экране.

## Как течёт информация

```
msu.tj (enf.xls, gf.xls)  →  backend качает и парсит  →  Postgres (Neon)  →  REST API /api/*
                                                                      ↑
                                                       прокси на Vercel: /backend/* → /api/*
                                                                      ↑
                                                       web (Vercel) и mobile (APK)
                                                       только рисуют ответ API
```

- Синхронизация при старте и по таблице в `services/scheduler.py` (время Душанбе):
  суббота 10:00–16:00 — раз в 5 минут (по живым данным новая неделя выходит в сб
  между 11 и 13, правки — до ~15); пт/сб вечер и воскресенье — раз в 15 минут;
  будни 7–21 — раз в 30 минут; остальное — раз в 2 часа. Каждая проверка — HEAD-запрос
  (дата изменения файла), файл качается, только если дата поменялась. При частой
  проверке, если msu.tj не ответил на HEAD, файл **не** качаем (`require_head`).
  `CHECK_INTERVAL_HOURS` в настройках больше не используется, но поле оставлено:
  переменная может быть задана на Render, а лишние переменные pydantic отвергает.

### Уведомления о расписании

- **Новая неделя** → push всем группам факультета: «Вышло расписание на новую неделю» /
  «Неделя 5–10 окт» (`notify_new_week`). Объявляется только если в базе уже была более
  ранняя неделя этого факультета, а новая позже всех (`announce_new_week` в
  `save_schedule_to_db`). Проверка писалась под эфемерную базу (после деплоя «новыми»
  оказались бы все недели); с Postgres она защищает первое наполнение пустой базы и
  откат файла к старой неделе. Запись `new_week` в ленту пишется по тому же условию.
- **Правки внутри недели** → push только изменившейся группе, строго по `group_id`
  (раньше искали по названию, а оно одинаковое у всех курсов направления).
- Оба канала сразу: Web Push (сайт) и Expo (приложение). Ответ Expo разбирается по
  каждому токену: `InvalidCredentials` = в Expo не загружен ключ Firebase,
  `DeviceNotRegistered` = токен стирается. Тестовый push в `/dev` шлёт в оба канала.
- **Новая версия приложения** → push «Вышла новая версия» / «МГУ Расписание 1.9.38 —
  нажмите, чтобы скачать» тем, у кого версия старее (`notify_app_update`). Задача
  `app_update_check` раз в 10 минут с 8 до 22 смотрит GitHub Releases; только релиз
  моложе 3 дней; каждому телефону один раз на версию (`app_update_notices`). Версию
  телефон сообщает сам (`app_version` в `/user/register` и `/user/push-token`, с 1.9.37);
  NULL = версия старее. Тап по уведомлению открывает ссылку на APK.
- Клиенты сами тихо перерегистрируются (`/user/register?silent=1` без письма владельцу,
  push-токен приложения, web-push подписка сайта) при запуске и возврате в приложение.
  Писалось, пока база стиралась при деплое; с Postgres это страховка (смена токена и т. п.).
- Напоминания о зачётах с сервера (07:00: «завтра» и «сегодня», плюс «на следующей неделе»
  после синхронизации) уходят **только в Web Push** (сайт). Приложение ставит свои,
  локальные (накануне 20:00 и в день 07:00) — каналы не пересекаются, дублей нет.
- HTML-страницы расписания на msu.tj закрыты анти-ботом (HTTP 416) — скрапить нельзя.
  Файлы XLS не закрыты, их и качаем. Мёртвый код скрапера остался в `parser.py`
  за флагом `SCRAPE_HTML_TEACHERS = False` — на случай, если защиту снимут.

### ⚠️ Никто не ходит на Render напрямую

**Megafon TJ (мобильный интернет) молча роняет пакеты до IP-диапазона Render
`216.24.57.0/24`.** Проверено 31 августа 2026 с телефона при выключенном Wi-Fi:
не открывается ни `msu-schedule.onrender.com`, ни голый IP `216.24.57.7`
(то есть дело не в DNS и не в имени хоста), ни любой чужой сервис на
`onrender.com` — везде `ERR_CONNECTION_TIMED_OUT`. Через VPN всё работает.
На Wi-Fi всё работает. IPv6 ни при чём: Megafon выдаёт чистый IPv4.

Поэтому клиенты ходят на бэкенд **через прокси на Vercel**:

```
https://frontend-ten-nu-80.vercel.app/backend/*  →  https://msu-schedule.onrender.com/api/*
```

- правило прокси — `frontend/next.config.ts`, `rewrites()`;
- адрес для веба — там же, `env.NEXT_PUBLIC_API_URL = "/backend"` (путь, а не URL,
  и зашит литералом: переменная со старым адресом Render в настройках Vercel
  снова сломала бы мобильный интернет);
- адрес для мобильного — `app.json → expo.extra.apiUrl` в репозитории мобилки;
- `/health` продублирован как `/api/health` — иначе он не попадает в префикс прокси;
- `.github/workflows/keepalive.yml` не даёт Render заснуть в 07:00-23:00 по Душанбе,
  чтобы прокси не ждал холодного старта.

**Не возвращайте прямые ссылки на `onrender.com` в код клиентов.** Ретраями и
длинными тайм-аутами это не лечится — пробовали дважды (v1.9.18, v1.9.19),
оба раза мимо: пакеты просто не доходят, сколько ни повторяй.

### Что фиксируется как «изменение»

`detect_changes` (`services/sync.py`) сравнивает новую версию недели с предыдущей версией
**той же** недели по предмету, аудитории, преподавателю и типу пары. В записи
`ScheduleChange`: `old_value`/`new_value` — краткая подпись (названия предметов, если сменился
предмет; иначе «ауд. 105» → «ауд. 402» и т. п.) и `old_details`/`new_details` — JSON
`{subject, room, teacher, lesson_type}` до и после. Отдаются в `/api/schedule/changes`.
Аудитория и тип сравниваются без учёта регистра, преподаватели — как множество; смена
преподавателя не считается, если с одной стороны там код кафедры (без инициалов) —
иначе правка в `/dev` → «Замены ФИО» выглядела бы «заменой преподавателя».
`new_week` пишется одной записью на факультет, без деталей.

### База — Postgres на Neon (с 4 окт 2026)

`DATABASE_URL` на Render → Environment указывает на Neon (бесплатный тариф). Регистрации,
подписки и история изменений теперь **переживают деплой**. `/health` показывает `"db"`:
`postgresql` — внешняя база, `sqlite` — переменная слетела и база снова эфемерная.

- Адрес из Neon (`postgresql://…?sslmode=require`) вставляется как есть — `config.py` сам
  дописывает драйвер `psycopg`. Без `DATABASE_URL` — SQLite (только для локального запуска).
- Neon усыпляет базу после ~5 минут простоя и рвёт соединения: в `database.py`
  `pool_pre_ping` и `pool_recycle=300`. Первый запрос после сна — на секунду-две дольше.
- Таблицы и недостающие колонки создаёт `lifespan` в `main.py` при каждом старте
  (идемпотентно: `create_all` + `ALTER TABLE … ADD COLUMN`, только если колонки нет).
- **Отличия от SQLite, на которые уже наступали:** Postgres проверяет внешние ключи
  (удаление архивной пары, на которую ссылается `attendance_records`, роняло бы
  синхронизацию — чистится в `cleanup_old_schedules`) и длину строк (`String(100)` —
  это 100, а не «сколько угодно»: длинное имя при регистрации давало 500).
- Лимит бесплатного Neon — 0,5 ГБ. Сейчас база — единицы мегабайт: архив недель
  чистится через 14 дней, `sync_logs` — через 14 дней. Без чистки растут только
  `schedule_changes` (сотни строк в неделю), `user_registrations` и `exam_notification_logs` —
  на годы хватит.
- **Часы работы Neon — главный лимит при росте** (8 окт 2026, ~100 пользователей): бесплатно
  100 CU-часов в месяц = ~400 часов при 0,25 CU. Кончатся — Neon выключает базу до 1-го числа,
  и встаёт всё. Поэтому база должна днём спать: готовые ответы `/api/schedule/*` хранятся в
  памяти (`core/response_cache.py`), а тихая перерегистрация телефонов (раз в 30 мин) не пишет
  в базу, если ничего не поменялось (`_saved_reg` / `_saved_token` в `user.py`). Расход
  смотреть в панели Neon → Usage; максимум автомасштаба держать 0,25 CU.
- Ранее в этом файле было написано, что база на volume и переживает деплой, потом — что
  она эфемерная SQLite. Актуально то, что выше.

### ⚠️ id групп считаются, а не выдаются по порядку

Раз база пересоздаётся, автоинкрементные id из порядка вставки были ловушкой:
`sync_all()` синхронизирует оба факультета через `asyncio.gather`, и кто первым допишет
свои группы — как повезёт. 31 августа 2026 после деплоя «ПМиИ 3 курс» из группы №7 стала
№19, а №7 досталась «Международным отношениям». Клиенты хранят выбранную группу по id —
и человек молча начинал смотреть чужое расписание: название на экране своё, из локального
кэша, а пары чужие. Ошибка без единого сообщения об ошибке.

Теперь id считается из факультета, курса и названия — `stable_group_id()` в `models.py`,
задаётся явно в `get_or_create_group()`. Не зависит ни от порядка вставки, ни от появления
новых групп выше по списку. **Не возвращайте автоинкремент.**

Вторая линия обороны — на клиентах: рядом с id хранится «отпечаток» группы
(`selected_group_pin` = `курс|НАЗВАНИЕ`), и при расхождении верят ему, а не номеру
(`repairSavedGroup` в `frontend/src/lib/api.ts` и в `src/api.ts` мобилки). Если не сошлось
ничего — выбор стирается и человека просят выбрать группу заново. Показать пустой экран
честнее, чем чужое расписание.

## Backend — ключевые файлы (`backend/app/`)

- `main.py` — запуск, lifespan (создание таблиц, индексы, миграция колонки `week_start`,
  `seed_rooms()` — чистка и дедуп аудиторий, `load_teacher_overrides()`, первая синхронизация), CORS.
- `core/config.py` — настройки из переменных окружения.
- `models.py` — таблицы: Faculty, Group, Teacher, Room, WeekSchedule, Lesson, ScheduleChange,
  UserSubscription, LessonNote, AttendanceRecord, UserRegistration, SyncLog,
  ExamNotificationLog, **TeacherOverride** (ручные замены ФИО).
- `services/parser.py` — разбор XLS (`parse_xls_file`, `parse_subject_cell`, `parse_room`),
  карта замен ФИО.
- `services/sync.py` — скачать → распарсить → сохранить → найти изменения → сбросить кэш → push.
  `sync_all` / `sync_faculty` идут **в отдельном потоке со своим циклом** (`_off_loop`): внутри
  всё блокирующее (XLS, сотни запросов к базе, рассылка push), и в основном цикле сервер на это
  время не отвечал никому. Стартовая синхронизация — в фоне, сервер после сна отвечает сразу.
- `core/response_cache.py` — кэш готовых (уже сжатых) ответов GET `/api/schedule/*`, кроме
  `/now`. Сброс — `clear_free_rooms_cache()` (поколение), смена даты Душанбе в ключе, час.
  Одинаковые одновременные запросы ждут первый: после push все телефоны группы разом просят
  `/bulk-sync`, а считается он один раз.
- `services/scheduler.py` — проверка msu.tj (тик раз в 5 мин, частота по `sync_interval_minutes`)
  + ежедневные напоминания о зачётах в 07:00.
- `services/push.py` — web-push (VAPID) и Expo. `send_push` возвращает `bool`,
  `send_expo_push` — `{"sent", "errors"}`.
- `api/routes/schedule.py` — основные эндпоинты, `enrich_lesson`, кэш свободных аудиторий.
- `api/routes/user.py` — регистрация, подписки, web-push.
- `api/routes/admin.py` — ручная синхронизация по заголовку `X-Admin-Secret`. **Все** маршруты закрыты ключом.
- `api/routes/dev.py` — скрытая панель разработчика (см. ниже).
- `api/routes/app_update.py` — `/api/app/version`: отдаёт последнюю версию мобильного из GitHub Releases.
- `api/routes/export.py` — экспорт в `.ics`.

### Кэш ответов API (`lib/api.ts`)

Стратегия — **stale-while-revalidate**, два уровня хранения:

| Уровень | Живёт | Зачем |
|---|---|---|
| память (`Map`) | пока открыта вкладка | переходы между страницами без единого запроса |
| `localStorage` (`msu_api_v1:*`) | до 7 дней, до 60 записей | первый экран рисуется мгновенно даже на спящем Render |

- Свежее (моложе TTL) — отдаём сразу, в сеть не идём.
- Протухшее — отдаём сразу **и** обновляем в фоне; когда данные реально изменились,
  срабатывает `onApiUpdate`, и страница молча перечитывает себя.
- Сети нет — отдаём сохранённое любого возраста. Это и есть офлайн-режим сайта.
- `/schedule/now` помечен `volatile`: он привязан к текущей минуте, в `localStorage`
  не пишется и из прошлой сессии не показывается.
- Ручной сброс — `clearApiCache()`. Перезапросить всё закэшированное мимо TTL —
  `revalidateCached()` (зовётся, когда service worker получил push).
- Список недель живёт 5 минут (`TTL_WEEKS`) и перезапрашивается при возврате на вкладку:
  так сайт узнаёт о вышедшей в субботу новой неделе без ручного обновления.

Один и тот же путь, запрошенный двумя компонентами одновременно, уходит в сеть **один раз**
(дедупликация по пути). Тайм-аут 15 сек; если показать нечего, одна повторная попытка
с тайм-аутом 40 сек — на случай, когда Render просыпается.

### ⚠️ Главная ловушка веба (hydration #418)

Все страницы `"use client"`, но Next.js всё равно делает SSR. Читать `localStorage`
или `new Date()` прямо в инициализаторе `useState` **нельзя** — первый клиентский рендер
разойдётся с серверным. Инициализируй нейтральным значением, реальное ставь в `useEffect`.

Побочный эффект: `npm run lint` даёт ~15 ошибок `react-hooks/set-state-in-effect` —
это цена принятого паттерна, не баги. Сборку они не ломают.

Проверка перед пушем: `cd frontend && npx next build` — должно быть 0 ошибок.

- Аудитории в нижнем регистре (чтобы «лабФИЗ» и «лабфиз» были одной).
- `/free-rooms` отдаёт **все** группы в занятой аудитории (`occupied_list`) и флаг `conflict`,

## Пропуски и заметки

До 1 сентября 2026 они были закрыты замком по дате; замок убран (окт 2026) вместе с
одноразовой подсказкой FeatureHint. Функции по умолчанию **выключены** — каждый
пользователь включает их сам в «Моём кабинете». Это задумано, не баг.

**Пропуски.** Отмечается только то, что пропустил; отсутствие отметки у прошедшей пары = «был».
Кнопка есть только у пар, которые уже прошли, и не показывается на экзаменах и зачётах.
Статистика — «пропущено N пар» с разбивкой по предметам.

**Заметки.** По умолчанию закрепляются за слотом «день + пара» и повторяются каждую неделю;
галочкой можно сделать разовой, привязанной к дате.

Данные хранятся **только на устройстве** (localStorage / AsyncStorage), на сервер не уходят.
Переустановил приложение или зашёл с другого телефона — данных нет. Серверные таблицы
`lesson_notes` и `attendance_records` и эндпоинты `/api/user/notes`, `/api/user/attendance`
существуют, но **фронты их не вызывают**.

  скрипт и гонять на боевом коде с синтетическими данными. Так проверялись перемены,
